[[ssl-certs-import]]
= 导入 SSL 证书
:description: 导入 SSL 证书以配置全新安装，或用 PEM 格式的正确私钥、证书和 CA 链文件替换已有证书。
:revdate: 2026-08-12
:page-revdate: {revdate}

//By default, {productname} uses a self-signed certificate.
//For additional security, you can import a custom certificate, signed by a third party certificate authority (CA).

本节介绍如何为新的 {productname} 安装配置 SSL 证书，以及如何替换现有证书。

在开始之前，请确保已准备好：

* 证书颁发机构 (CA) 的 SSL 公共证书。
  如果您使用 CA 链，则所有中间 CA 也必须可用。
* 一个 SSL 服务器私用密钥
* 一个 SSL 服务器证书
* 一个 SSL 数据库私用密钥
* 一个 SSL 数据库证书

所有文件必须采用 PEM 格式。
链中的所有 CA 证书都必须将 `X509v3 Basic Constraints` 标记为 `critical` 并包含 `CA:TRUE`。
有关详细信息，请参见 xref:administration:ssl-certs-imported.adoc#ssl-certs-verify-ca-basic-constraints[]。

SSL 服务器证书的主机名必须与其部署到的计算机的完全限定主机名相匹配。
您可以在证书的 `X509v3 Subject Alternative Name` 部分中设置主机名。
如果您的环境需要，您还可以列出多个主机名。
支持的密钥类型为 `RSA` 和 `EC`（椭圆曲线）。

[IMPORTANT]
====
在以前的版本中，数据库 SSL 证书需要 `reportdb` 和 `db` 作为 `Subject Alternative Name`。
这已经不再需要。
====

第三方机构通常使用中间 CA 来签署请求的服务器证书。
在这种情况下，链中的所有 CA 都需要可用。
`mgradm` 命令负责排序证书。
理想情况下，根 CA 应该在其自己的文件中。
服务器证书文件应首先包含服务器证书，然后按顺序包含所有中间 CA 证书。



[[ssl-certs-verify-ca-basic-constraints]]
== 验证 CA 基本约束

当 `X509v3 Basic Constraints` 扩展未标记为 `critical` 时，严格的证书验证程序会拒绝 CA 证书。
这包括 {sles} 16 和 openSUSE Leap 16 所使用的 Python 3.13 及更高版本。

在导入证书或升级现有安装之前，请验证 {productname} 使用的每个 root CA 证书和中间 CA 证书。
对于每个 CA 证书，请运行：

[source,shell]
----
openssl x509 -in root-ca.pem -noout -text | grep -A1 "Basic Constraints"
----

输出必须包含 `critical` 和 `CA:TRUE`：

[source]
----
X509v3 Basic Constraints: critical
  CA:TRUE
----

如果 CA 证书未包含这两个值，请在将其与 {productname} 一起使用之前替换或重新生成受影响的 CA 证书。
仅替换服务器证书无法修复缺少 `critical` 标志的 CA 证书。
有关 {productname} 生成的自签名证书，请参见 xref:administration:ssl-certs-selfsigned.adoc#ssl-certs-selfsigned-create-replace[]。
要替换客户端仍信任的 CA 且不中断其连接，请参见 xref:administration:ssl-certs-ca-migration.adoc[]。



== 为新安装导入证书


默认情况下，{productname} 使用自签名证书。
证书可以在安装时与第三方证书一起导入。

.过程：升级在新的 {productname} 服务器上导入证书
[role=procedure]
_____
. 根据 {productname} 中的说明部署 xref:installation-and-upgrade:install-server.adoc[] 服务器。
  确保将正确的文件作为参数传递给 `mgradm install`。
  这些参数是：

+

----
3rd Party SSL Certificate Flags:
      --ssl-ca-intermediate strings    Intermediate CA certificate path
      --ssl-ca-root string             Root CA certificate path
      --ssl-server-cert string         Server certificate path
      --ssl-server-key string          Server key path
      --ssl-db-ca-intermediate strings Intermediate CA certificate path for the database if different from the server one
      --ssl-db-ca-root string          Root CA certificate path for the database if different from the server one
      --ssl-db-cert string             Database certificate path
      --ssl-db-key string              Database key path
----
_____

中间 CA 可以在指定的 `--ssl-ca-root` 文件中可用，或者作为额外选项指定 `--ssl-ca-intermediate`。
`--ssl-ca-intermediate` 选项可以多次指定。



== 为新的 Proxy 安装导入证书

代理证书嵌入在生成的配置中。
为了使用第三方证书，需要在配置期间提供该证书。

.过程：升级在新的 {productname} 代理上导入证书
[role=procedure]
_____
. 根据 {productname} 中的说明安装 xref:installation-and-upgrade:install-proxy.adoc[] 代理。

. 按照提示完成设置。

+

[NOTE]
====
使用相同的证书颁发机构（CA）为服务器和代理签署所有证书。
使用不同 CA 签署的证书不匹配。
====

_____


[[ssl-certs-import-replace]]
== 替换证书


您可以用新证书替换 {productname} 安装上的活动证书。
需要考虑两种情况：仅替换服务器或数据库证书，以及替换根 CA。


替换根证书需要更多时间并进行更多规划，以避免服务中断，因为在服务器层面切换至新证书前，所有已注册的代理和系统都需要在其数据库中导入新的 CA 证书。

使用由中间 CA 签名的第三方证书时，需要将中间 CA 证书追加至服务器或数据库证书文件中。

顺序很重要：首先是服务器证书，然后是从签署证书的 CA 到根 CA 签署的 CA。
根 CA 证书不应附加到服务器证书文件中。


.过程：升级替换所有现有证书
[role=procedure]
_____
. 以下内容假设您拥有 `root-ca.pem`、`intermediate-ca1.pem`、`intermediate-ca2.pem`、`server.pem` 和 `server.key` 文件。
  这可能会因服务器证书签名链中中间 CA 的数量而有所不同。

. 组合中间 CA 和服务器证书。
  顺序很重要，服务器必须在前，中间 CA 按顺序排列。
  请勿将 root CA 最后添加到链中，因为它将分别传递给 `uyuni-ca` 和 `uyuni-db-ca` 机密。
  如果没有中间 CA，则可以在接下来的步骤中使用 `server.pem` 而不是组合文件。

+
[source,shell]
----
cat server.pem intermediate-ca1.pem intermediate-ca2.pem >combined-server.pem
----

. 在 {productname} 容器主机上，在命令提示符下，使用 `mgradm ssl rotate` 轮换证书：

+
[source,shell]
----
mgradm ssl rotate \
   --ssl-ca-root $path_to_ca_certificate \
   --ssl-server-cert $path_to_combined_server_certificate \
   --ssl-server-key $path_to_server_key
----
_____

[[ssl-certs-import-replace-proxy]]
== 替换代理上的证书

如果您正在使用 {productname} 代理，则在替换 {productname} 服务器上的证书后，必须重新生成并重新部署代理的配置。
这可确保代理信任服务器的新 CA，并使用其自身更新后的服务器证书。

不支持使用 Web UI 生成代理配置来替换证书。您必须从命令行使用 `spacecmd`。

.过程：升级替换 {productname} 代理上的证书
[role=procedure]
_____
. 在您的 {productname} 服务器容器主机上，将根 CA 证书（`ca.crt`）、代理证书（`proxy.crt`）和代理私钥（`proxy.key`）复制到服务器容器中：
+
[source,shell]
----
for f in ca.crt proxy.crt proxy.key; do
  mgrctl cp $f server:/tmp/$f
done
----

. 如果您的环境使用一个或多个中间 CA，也请将它们复制到容器中：
+
[source,shell]
----
mgrctl cp intermediateCA.pem server:/tmp/intermediateCA.pem
----

. 在服务器容器内执行 `spacecmd proxy_container_config` 以生成新的配置归档文件，并替换 FQDN 和管理员电子邮件：
+
[source,shell]
----
mgrctl exec -ti 'spacecmd proxy_container_config -- -p 8022 pxy.example.com srv.example.com 2048 email@example.com /tmp/ca.crt /tmp/proxy.crt /tmp/proxy.key -o /tmp/config.tar.gz'
----
+
如果您在上一步中复制了中间 CA，请附加 `-i` 参数：
+
[source,shell]
----
mgrctl exec -ti 'spacecmd proxy_container_config -- -p 8022 -i /tmp/intermediateCA.pem pxy.example.com srv.example.com 2048 email@example.com /tmp/ca.crt /tmp/proxy.crt /tmp/proxy.key -o /tmp/config.tar.gz'
----

. 将生成的配置归档文件从服务器容器复制到服务器主机：
+
[source,shell]
----
mgrctl cp server:/tmp/config.tar.gz .
----

. 将 `config.tar.gz` 归档文件传输到代理主机：
+
[source,shell]
----
scp config.tar.gz root@pxy.example.com:/root/
----

. 在代理主机上，停止代理：
+
[source,shell]
----
mgrpxy stop
----

. 在代理主机上安装新配置：
+
[source,shell]
----
mgrpxy install config.tar.gz
----

. 启动代理：
+
[source,shell]
----
mgrpxy start
----
_____



如果根 CA 已更改，则需要将其部署到与 {productname} 连接的所有客户端。
理想情况下，应提前完成此操作以最小化干扰。

[[ssl-certs-import-deploy-root-ca]]
.过程：升级在客户端上部署根 CA
[role=procedure]
_____
. 在 {productname} {webui} 中，导航到 menu:系统[概述]。

. 选中所有客户端以将其添加到系统集管理器。

. 导航到 menu:系统[系统设置管理器> 概述]。

. 在 `States` 字段中，单击 btn:[应用] 以应用系统状态。

. 在 `Highstate` 页面中，单击 btn:[应用高状态] 以将更改传播到客户端。
_____
